# ENTprep — Full Project Audit

_Generated 2026-06-16 · 13 dimensions · 27 agents · every medium-and-above finding adversarially re-checked against the code before inclusion._

## Methodology

Each of 13 audit dimensions was reviewed by a dedicated agent that read the actual source and filed findings with `file:line` evidence. A second, adversarial agent per dimension independently re-read the code to **confirm, refute, or re-scope** each medium+ finding — refuted claims are moved to the appendix, not the report body. A final agent synthesized the executive summary below. **101 findings** survived verification (3 critical, 17 high, 34 medium, 40 low, 7 info); 0 were refuted/not reproduced.

## Executive summary

**Health score:** 6.5/10 — strong, broad product; serious but fixable payment-integrity, trust, and data-correctness gaps

ENTprep is a genuinely impressive product for a solo non-professional founder: 13 subjects, ~31k questions, full ЕНТ simulation, bilingual content, AI features, social/duels, and live paying users on entprep.org. The frontend product surface is broad and the team has clearly invested in a design system, a typed locale layer, a 357-test suite, and even documented deploy-safety lore (the Supabase-env predeploy gate). That maturity is real and worth protecting.

The problem is that the money and trust layer — the part that converts users into revenue and keeps their data honest — has not gotten the same rigor. Two payment paths can hand out free Premium (the Lemon self-reconcile lets anyone claim a paid order ID, and the RevenueCat webhook has no idempotency so replays re-grant), the client trusts a value users can edit to mark themselves Premium, payment webhooks have zero tests and zero error reporting (so a broken payment is silently invisible), and the deploy gate everyone relies on is bypassed entirely on Netlify auto-deploys. Layered on top is a correctness landmine in the content itself: 195 questions grade Kazakh users against the wrong answer because the translated options were reordered but the correct-index was not — that directly erodes trust with half your audience. None of these are exotic; they are concrete, cited, and fixable in days, not months. The verdict: a strong product sitting on a soft financial/integrity foundation. Spend the next sprint plugging the revenue leaks and the Kazakh grading bug before adding any new features.

### 🔥 Top risks

- **SEC-1 / PAY-1: Lemon self-reconcile gives away free Premium (order theft + farm)** — lemon-reconcile.mjs:118-153 activates Premium from any 'paid' order ID with no check that the order's payer email matches the logged-in user and no idempotency. One leaked order ID can be claimed by unlimited accounts. This is the single most direct revenue leak — verified in code.
- **PAY-2 / SEC-2: RevenueCat webhook has zero idempotency — replays double-grant Premium and double-insert payments** — revenuecat-webhook.mjs:142-183 never checks whether an event was already processed. Duplicate/replayed deliveries re-extend Premium and corrupt payment records. The rc_${eventType} fallback id is worse — it collapses all events of a type to one id. No UNIQUE constraint on payments.kaspi_tx_id exists as a backstop (PAY-7).
- **PAY-3: Client-writable user_metadata is trusted as a Premium source — self-grant bypass** — AuthContext.tsx:176-184 falls back to user_metadata.is_premium / premium_until, which the client can write. A user can mark themselves Premium without paying. Should rely only on the DB subscriptions row and native RevenueCat.
- **I18N-1: 195 questions grade Kazakh users against the WRONG answer** — o_kk options were reordered but the shared correct-index c was left stale (chemistry 64, physics 41, math 35, english 27, and more). Kazakh users — half the audience — are marked wrong on correct answers. This silently destroys trust and is a refund/churn magnet.
- **OPS-1 + OPS-2: The deploy safety gate is bypassed on Netlify auto-deploy, and all 18 Functions have zero error reporting** — predeploy-check.mjs only runs in the manual chain (netlify.toml:1-3); any Netlify auto-publish ships without it — the documented protection is a false sense of safety. Combined with no Sentry in any Function, a broken payment webhook fails completely silently. You'd learn about a revenue outage from angry users, not alerts.

### ⚡ Quick wins

- **Add a UNIQUE constraint on payments.kaspi_tx_id and treat 23505 as idempotent success** — One DB migration closes the hard backstop for BOTH RC replay (PAY-2) and Lemon double-claim (PAY-1) races at once. Cheap, high-leverage, and makes the idempotency guarantee enforceable instead of best-effort SELECT-then-INSERT.
- **Delete the user_metadata branch from isPremium (PAY-3)** — A few lines removed in AuthContext.tsx:176-184 closes the client self-grant bypass. dbPremium + nativePremium already cover the real cases; the metadata write can stay as a legacy cache, just never a source of truth.
- **Run the o_kk correct-index fix script for the 195 mis-keyed questions (I18N-1)** — Precedent scripts exist (fix-english-kk.mjs). A one-off reorder/c_kk fix + re-dump immediately stops grading Kazakh users wrong — biggest trust win per hour of effort.
- **Set RC monthly recorded amount to 2990 (PAY-4)** — One-line constants.mjs fix; every monthly payment is currently logged at 1990 while customers were charged 2990 — corrupt financial records that will bite at accounting/refund time.
- **Bump vitest to 4.1.9 and vite within v6 (DEP-5, DEP-6)** — DEP-5 is a CRITICAL advisory (UI server arbitrary file read+exec); both are in-range patch bumps with near-zero risk. Removes real security noise in minutes.
- **Wire predeploy-check + npm test into the active CI/Netlify path (OPS-1, OPS-3, TEST-10)** — Makes the existing safety net actually run on every deploy instead of relying on shell discipline — prevents a repeat of the silent auth-break incident and lets a red suite block deploy.
- **Delete dead code: aiMemory.ts, Home.tsx, Subjects.tsx, scorePrediction.ts or predictScore.ts, qrcode dep (TS-1, ARCH-4, TS-2, DEP-2)** — Removes ~700+ lines of confusing dead code (including the nested-interactive markup likely behind the 'taps don't respond' report) and an unused dependency, with no behavior change.

## Findings by dimension

### Security &amp; secrets (SEC)

> The backend has a notably mature security posture for a solo-built app: webhook signatures are verified with timing-safe comparison, the leaderboard recomputes scores server-side from the DB (not trusting client-submitted scores), the Supabase service-role key is confined to Netlify Functions (never inlined in the client bundle — only the public anon key is), secrets are correctly gitignored, RLS is enabled with sensible policies on profiles/friendships/subscriptions, and most functions enforce auth + per-user rate limiting + input validation. The most serious gap is in the payment-recovery path: `lemon-reconcile` mode=self lets any authenticated user claim ANY valid paid Lemon order ID as their own premium, with no check that the order belongs to them and no guard against re-claiming an already-redeemed order. Secondary issues: the RevenueCat webhook has no idempotency guard (unlike the Lemon webhook), several PostgREST filters interpolate user/DB-derived values without `encodeURIComponent` (notably the duel `code`), and the `payments`/`audit_logs` tables that back idempotency and admin auditing are not defined in the repo's migrations, so a unique constraint on `kaspi_tx_id` cannot be confirmed.

**Strengths**

### Payments & monetization integrity (PAY)

> The payment architecture is reasonably defensive in places — webhook signatures are HMAC/timing-safe verified, the `subscriptions` table is the authoritative source with service-role-only writes via RLS, and Lemon's webhook has a SELECT-based idempotency guard. However there are real integrity gaps that cost money and corrupt records: (1) the RevenueCat webhook has NO idempotency check at all (every duplicate delivery inserts a duplicate payment row and re-extends premium); (2) Lemon self-reconcile lets the SAME paid order ID be claimed by unlimited different accounts (no per-order claim ledger), turning one purchase into many free premiums; (3) the `payments.amount` for every monthly subscriber is recorded as the stale 1990 while the user was actually charged 2990, corrupting revenue/accounting/refund records; (4) the `is_premium` user_metadata fallback in `isPremium` is client-writable, so any user can self-grant client-side premium (gating all paywalled UI off); (5) promo `used_count` increment is a non-atomic read-modify-write that lets concurrent redemptions blow past `max_uses`; and (6) an RC EXPIRATION event blindly clobbers the single per-user subscription row, wiping a still-valid promo/Lemon grant. Note: the most damaging "premium" features (AI explain, AI plan, Full-ENT) are not actually server-gated — only ai-tutor is — so the client-side bypass mostly unlocks the Full-ENT result paywall and tutor message cap rather than the core AI features (which are already free).

**Strengths**
- Both webhooks verify authenticity with constant-time comparison: revenuecat-webhook.mjs uses timingSafeEqual on a Bearer secret (lines 113-119), lemon-webhook.mjs uses HMAC-SHA256 over the raw body with timingSafeEqual (lines 45-51). Signatures are checked before any body parsing.
- The subscriptions table is a proper authoritative source: service-role-only writes enforced by RLS (20260316_subscriptions_table.sql lines 13-20, no INSERT/UPDATE policy for authenticated), and the server-side checkPremium() (shared.mjs 143-162) reads it with the service key. ai-tutor.mjs gates premium on this server-side value (line 92), not on client claims.
- Lemon webhook has real idempotency: it checks the payments table for an existing kaspi_tx_id before activating (lemon-webhook.mjs 122-133), and distinguishes initial vs renewal payments via a RENEWAL_WINDOW check to avoid triple-logging (97-120).
- promo_redemptions enforces UNIQUE(promo_id, user_id) at the DB level (20260319_promo_codes.sql line 20), so a single user genuinely cannot double-redeem the same code even though the application-level check is racy.
- Apple Guideline 3.1.1 is correctly handled: PaywallScreen routes all native paywall surfaces to RevenueCat StoreKit (PaywallScreen.tsx 22-35,114-119) instead of the Lemon web checkout, avoiding a rejection/ban risk.
- The lemon-reconcile self mode validates the order is paid AND belongs to the configured store before activating (lemon-reconcile.mjs 132-138), blocking cross-store order claims.
- ai-tutor uses a single shared rate-limit bucket with a per-request cap override so a free->premium transition mid-window cannot reset the counter (ai-tutor.mjs 15-17, shared.mjs 50-51).

### Architecture & maintainability (ARCH)

> The architecture is pragmatic and well-suited to a single-developer product: a clean 4-context provider tree, lazy-loaded route components wrapped in per-screen ErrorBoundaries, and a thoughtfully layered question-loading pipeline (memory → CDN JSON → Supabase → localStorage → static bundle) with abort timeouts, request de-duplication, and a partial-data-over-null fallback. The main weaknesses are a hand-rolled string-based "screen" switch (NavigationContext) that reimplements a router poorly (no real history, no URL state, a 40-line if/else nav() and a duplicated 200-char showNav boolean), a top-level AppContent that subscribes to all four contexts so the whole tree re-renders on every state change, and a question-count data model with three disagreeing sources of truth (28,419 / 33,244 / 31,773). Dead code (Home.tsx, Subjects.tsx) and several near-duplicate copy-paste blocks in questionStore hurt maintainability but not users.

**Strengths**
- Layered question-loading strategy in questionStore.ts is genuinely well-engineered: CDN-first for speed, Supabase fallback with paginated fetch + 15s AbortController timeouts (questionStore.ts:151-170), request de-dup via a `pending` map so concurrent getPool(sid) calls share one fetch (questionStore.ts:260-263), and partial-data-over-null on page failure (line 168) so a flaky network degrades gracefully instead of breaking tests.
- Cloud-sync correctness is handled with real care: cloudLoad distinguishes 'empty' (PGRST116) from 'failed' (network/503) and callers refuse to overwrite cloud with empty local state on a fresh device (AppContext.tsx:119-126, cloudSync.ts:16-50) — this is the exact bug that wipes user history, and it's explicitly guarded with comments.
- Every lazy route is individually wrapped in an ErrorBoundary with a localized recover action (App.tsx:266-347), so a crash in one screen (Duel, FullENT, etc.) can't white-screen the whole app and the user can return home.
- Context values are memoized with useMemo and callbacks with useCallback throughout all four contexts, and finishAuthPrompt deliberately reads hist.length via functional setState to avoid adding it as a dependency (AppContext.tsx:228-234) — shows real awareness of re-render cascades.
- Good separation of pure logic into testable utils (scoringEngine, xpHelpers, srEngine, adaptiveHelpers, mergeData) kept out of components, backed by 357 tests; the deep-freeze of cached question objects (questionStore.ts:234-237) prevents accidental mutation of the shared memory cache.
- Deploy-safety discipline is encoded, not just documented: supabase.ts fails closed to null and predeploy-check.mjs gates deploys on the bundle actually containing Supabase env, addressing a real prior outage.

> ENTprep has a genuinely well-architected central token layer (COLORS/TYPE/FF/SP/R + CARD/BUTTON/ANSWER presets in constants/styles.ts, CSS-var palettes in constants/themes.ts) and a clearly written spec (DESIGN.md + docs/design-prompt.md).
